# 编码规范（通用）

本指南用于补充通用编码规范，适用于 Go、Python 与前端项目的日常开发。

## 设计原则
- 实现 **应当** 遵循 SOLID 原则，保持职责边界清晰、依赖方向稳定、扩展方式可控
- 实现 **应当** 遵循 DRY 原则，避免同一语义或同一规则在多处重复实现
- 避免为了形式上的 DRY 合并语义不同的逻辑；复用 **应当** 建立在真实共享的概念或规则之上
- 实现 **应当** 优先保持简单直接，不为未确认的未来需求预埋抽象、配置或扩展点
- 新增抽象 **应当** 有明确收益，例如稳定接口隔离、重复逻辑收敛、跨实现一致性或复杂流程分层
- 兼容逻辑 **必须** 有明确来源；临时迁移、调试遗留、反复修改产生的别名、双入口和无调用方兼容层 **应当** 及时删除

## 注释与可读性
- 函数和结构体字段都 **应当** 有注释，确保其他开发人员能够理解其作用和场景，以及不同选项的影响
- 一些非常规的处理逻辑也 **应当** 有注释说明，避免其他开发人员理解错误
- 复杂流程建议拆分成小函数，每个函数表达单一职责
- 建议为关键业务路径补充示例用法或输入输出说明

## 配置与默认值
- 整体对于配置的处理 **应当** 遵从“约定优于配置”的设计逻辑，尽量根据最佳实践来初始化默认值，避免使用复杂的配置选项
- 对可选配置提供清晰默认值，并在入口处统一装配
- 对需要重启才能生效的配置进行标记，减少误用

## 错误处理
- 业务错误与系统错误分层处理，避免混用
- 关键分支 **必须** 返回可定位的错误信息
- **禁止** 吞掉错误或仅打印日志不返回错误

## 日志与追踪
- 日志字段 **应当** 保持稳定命名与结构化输出
- 入口层 **必须** 打出请求生命周期日志并透传必要 trace 标识

## 测试与质量
- 关键逻辑 **必须** 有单元测试覆盖，保证可回归
- 新增逻辑需补充最小用例，避免回归风险
