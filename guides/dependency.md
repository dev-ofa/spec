# 依赖实践指南（通用）

本指南定义跨语言通用的依赖管理实践，用于帮助团队在构造器注入、属性注入、全局单例、service locator 与 DI 系统之间做出一致选择。

本指南是 implementation guide，依赖管理的正文规则以 [dependency spec](../dependency/spec.md) 为准。本指南用于解释规范背后的取舍、判断顺序和常见实践。

## 目标

- 明确依赖管理中“生命周期”和“依赖发现方式”是两条独立维度。
- 避免团队在“所有东西都走构造器注入”和“所有东西都走全局单例”之间来回摇摆。
- 为 Go、Python 与其他语言实现提供统一的判断顺序与边界口径。

## 适用范围

- 服务端应用、后台任务、CLI、Worker 与基础设施适配层。
- 需要管理 repo、service、client、config、logger、metrics、tracer 等依赖的应用代码。

## 非目标

- 不强制某个具体 DI 框架、IoC 容器或代码生成工具。
- 不规定语言级语法、注解、装饰器或反射方案。
- 不要求所有项目都引入 DI 系统。

## 基本概念

### 生命周期

依赖生命周期描述某个依赖实例会活多久、会被多少调用方共享。

常见生命周期包括：

- transient：每次使用都新建一个实例。
- request-scoped：在单次请求、任务或会话内复用。
- singleton：在进程内共享一个实例。

### 依赖发现方式

依赖发现方式描述调用方如何拿到依赖引用。

常见方式包括：

- 构造器注入
- 属性注入
- service locator

生命周期和依赖发现方式不是同一概念。
例如，一个依赖 **可以** 是 singleton 生命周期，但仍通过构造器注入传给调用方。

## 依赖发现方式

### 构造器注入

构造器注入适用于需要显式表达依赖边界的场景。

优点：

- 调用方依赖显式可见。
- 更容易在测试中替换依赖。
- 更适合业务对象之间的协作关系建模。

代价：

- 当对象依赖过多时，构造参数会变长。
- 装配入口需要承担更多初始化代码。

构造器注入本身不决定生命周期，也不自动解决并发安全问题。
实现者仍然需要根据被注入依赖是否共享、是否有状态来评估线程安全或并发安全。

### 属性注入

属性注入 **可以** 作为补充方式存在，但通常 **不应** 作为默认方案。

原因：

- 依赖不如构造器注入显式。
- 容易出现对象已创建但尚未完成依赖装配的中间状态。
- 在测试、重构与阅读代码时更难判断对象是否完整可用。

如果项目确实使用属性注入， **应当** 明确对象何时进入“可用状态”，并避免依赖在运行中被随意替换。

### service locator

service locator 允许调用方通过全局发现入口获取依赖。

它适合用于稳定、技术基础设施类、生命周期通常为 singleton 的依赖，例如：

- 配置读取入口
- logger、metrics、tracer
- DB client、Redis client、HTTP client、MQ producer

service locator 不是默认 **禁止** 项，但 **必须** 满足以下前提：

- locator **必须** 由依赖提供方定义和维护。
- 调用方只能消费现成 locator， **不得** 在自己的模块中私自创建新的 locator、registry 或等价全局发现入口。
- locator 对外暴露的 **应当** 是稳定接口，而不是仅对某个实现成立的内部细节。
- provider **必须** 明确初始化顺序、失败语义、并发安全与测试替换策略。

如果这些前提做不到，优先回到构造器注入。

## 生命周期选择

### transient

适用于以下情况：

- 依赖本身有明显短生命周期语义。
- 实例保存了调用级状态，不适合共享。
- 创建成本低，且共享意义不大。

### singleton

适用于以下情况：

- 实例创建成本高。
- 需要复用底层连接、连接池或缓存。
- 进程内共享 **可以** 显著降低资源开销。

singleton 的代价是：

- 生命周期长。
- 会被共享。
- 实现者 **必须** 明确并发安全、初始化时机、关闭与重置语义。

singleton 适合描述实例作用域，但不自动决定调用方如何发现该实例。

## 推荐选择

### 业务协作依赖

对于偏业务的依赖，例如：

- repo
- domain service
- application service
- 业务 adapter

默认 **应当** 优先使用构造器注入。

原因：

- 这些依赖直接参与业务语义与副作用。
- 其边界 **应当** 显式。
- 调用方 **不应** 通过全局发现方式在运行中随意追加业务依赖。

### 静态与技术支撑类依赖

对于偏静态和技术支撑类的依赖，例如：

- 配置
- logger、metrics、tracer
- DB client、Redis client、HTTP client、MQ producer

通常更适合设计为 singleton 或其他共享生命周期。

调用方如何消费这些 singleton，有两种都成立的方案：

- 通过构造器注入显式引用
- 通过依赖提供方暴露的 service locator 发现

**应当** 根据以下因素选择：

- 当前团队是否更重视显式依赖边界
- 该依赖是否会被大量模块重复使用
- 测试替换与重置是否已经标准化
- provider 是否能够稳定治理 locator 入口

## 关于并发安全

生命周期越长、共享范围越广，越需要关注并发安全。

但并发安全不是由“构造器注入”或“service locator”自动决定的，而是由以下因素决定：

- 依赖实例是否共享
- 是否持有可变状态
- 是否暴露非线程安全或非并发安全操作

因此， **不应** 把“构造器注入”误解为“天然不需要考虑并发安全”，也 **不应** 把“singleton”简化成“只要加锁就安全”。

## DI 系统

DI 系统或 IoC 容器不是必选项。

它适合在以下情况引入：

- 装配图已经明显复杂，手写装配难以维护。
- 同一依赖存在多实现切换，且切换逻辑重复出现。
- 需要统一管理生命周期、初始化顺序与资源释放。

引入 DI 系统的代价包括：

- 学习成本
- 调试成本
- 语言生态支持差异
- 对框架、注解、反射或生成代码的额外依赖

因此，是否引入 DI 系统 **应当** 根据复杂度决定，而不是作为“工程先进性”的默认标志。

## 判断顺序

当一个新依赖进入系统时，推荐按以下顺序判断：

1. 它的生命周期是什么？
2. 它是偏业务协作依赖，还是偏静态/技术支撑类依赖？
3. 调用方是否需要显式暴露该依赖边界？
4. 如果使用 service locator，provider 是否能承担入口治理、初始化和测试替换责任？
5. 当前项目复杂度是否已经高到值得引入 DI 系统？

## 推荐实践摘要

- 先区分“生命周期”和“依赖发现方式”，不要把两者混为一谈。
- 业务协作依赖默认优先构造器注入。
- 静态与技术支撑类依赖通常适合共享生命周期。
- service locator **可以** 使用，但只能由依赖提供方暴露入口，不能由调用方私自创建。
- DI 系统在复杂度足够高时引入即可， **不应** 作为默认前置要求。
