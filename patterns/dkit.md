# DKit 介绍

## 状态
Draft

## 定位
- 本文是 patterns 规范的配套说明，用于解释 DKit 的工程思想和实现取舍，不作为独立规范约束。
- DKit（The Kit for Distributed Development）是 patterns 规范的一种工程化实现思路，用于轻量解决业务系统中常见的分布式协作问题。
- DKit 不是新的业务框架，也不是专用协调系统；它的核心目标是复用业务已有的事务数据库，以统一接口实现唯一 ID、分布式锁、选主、心跳、互斥 Worker 等分布式原语。
- DKit 适合已经拥有 MySQL、PostgreSQL、MongoDB 等事务存储的业务系统，尤其适合中小规模后台任务、管理面能力、低频临界区和演进早期的分布式协作需求。
- DKit 的设计重点不是追求极致性能，而是在可靠性、复杂度、成本和可演进性之间取得工程平衡。

## 核心理念
- 业务系统不应为了每一个分布式能力都立即引入独立组件。
- 事务数据库已经提供了唯一约束、条件更新、事务提交、持久化、查询和恢复能力，这些能力可以支撑大量常见分布式原语。
- 只要业务容量、失效恢复窗口和一致性要求允许，复用事务数据库通常比额外引入协调组件更简单、更可控。
- 当数据库实现无法满足容量、延迟、可用性或恢复窗口要求时，DKit 应允许底层实现平滑替换为 Redis、etcd、ZooKeeper、专用 ID 服务或消息系统。
- DKit 应通过稳定接口隔离业务代码与底层协作表结构，让业务先获得统一语义，再按需演进底层实现。

## 为什么复用事务数据库
- 事务数据库通常已经是业务系统的事实来源，不需要额外部署、监控和维护一套新基础设施。
- 数据库的唯一索引可以自然表达互斥、节点号占用、leader 占用和幂等去重。
- 数据库的条件更新可以表达 CAS 语义，用于抢占过期锁、续约 leader、释放持有者自己的资源。
- 数据库的事务可以把业务状态和协作状态放在同一个提交边界内，降低跨系统不一致风险。
- 数据库的持久化记录可以支持故障排查、状态恢复、人工介入和审计。
- 对多数业务后台任务而言，协作频率远低于核心数据读写频率，事务数据库可以承担这类轻量协作负载。

## 抽象模型
- DKit 应把底层存储抽象为一组分布式原语，而不是把表、集合、Redis key 或 SQL 暴露给业务。
- DKit 的核心对象可以分为 `Atomic`、`DistributedMutex`、`Election`、`Heartbeat`、`IDGenerator` 与 `WorkerGuard` 等能力。
- 每个原语都必须绑定明确的 `resource key` 或 `node key`，并应支持 `isolation key` 来隔离不同业务域。
- 所有临时状态都必须有 `ttl`、`expires`、`lease` 或等价过期机制。
- 所有阻塞、轮询、续约、抢占和释放操作都必须支持 context cancellation 或 timeout。
- 所有竞争失败、状态变化和后端异常都应提供可判断的错误语义，而不是依赖错误字符串。

## 事务数据库实现方式

### 唯一 ID
- DKit 可以使用事务数据库为雪花算法分配机器号或节点号。
- 节点启动时，在节点号表中通过唯一约束竞争一个可用编号。
- 节点号记录必须带有过期时间，避免异常退出后永久占用。
- 获取节点号后，ID 生成应在本地完成，避免每次生成 ID 都访问数据库。
- 当节点号池耗尽、数据库不可用或时钟回拨超过阈值时，ID 生成必须失败或降级，禁止生成可能冲突的 ID。

### 分布式锁
- DKit 可以用唯一索引表达锁资源的互斥占用。
- 获取锁时，对锁表执行按 `resource key` 唯一插入；如果记录已存在，则判断是否过期。
- 抢占过期锁时，必须使用条件更新校验旧 `expires`、版本或持有者标识，避免覆盖其他节点刚获得的新锁。
- 解锁时，必须校验持有者标识、版本、过期时间或 fencing token，禁止无条件删除同名锁。
- 锁必须有 ttl；业务执行时间可能超过 ttl 时，应续约、拆分任务或调整模型，而不是默认假设锁仍有效。

### 选主
- DKit 可以用一条 leader 记录表达同一 `isolation key` 下的 leader lease。
- 节点竞选时，通过唯一插入或条件更新抢占 leader 记录。
- leader 必须周期性续约，并在续约失败时主动放弃 leader 身份。
- follower 发现 leader 记录过期后，可以尝试竞选。
- 选主实现必须保证同一隔离域内同一时刻最多只有一个有效 leader。
- 实现应提供 `CanElect` 或等价机制，允许节点在本地健康检查失败、依赖不可用或人工摘除时拒绝参选。

### 心跳
- DKit 可以用心跳表记录节点存活状态。
- 节点定期对自己的心跳记录执行 upsert，并刷新过期时间。
- 查询存活节点时，必须过滤过期心跳。
- 节点正常关闭时，应尽力删除自己的心跳记录；异常退出时依赖过期机制自动清理。
- 心跳可以独立使用，也可以与选主组合使用，用于展示存活节点、辅助调度或判断节点健康。

### 互斥 Worker
- DKit 可以用分布式锁或选主能力保证某类后台 Worker 同一时间只在一个节点执行。
- Worker 开始执行前必须确认已经获得有效锁或 leader 身份。
- Worker 执行期间应周期性检查 context、lease 或 leader 状态。
- Worker 失去锁、失去 leader 身份、续约失败或收到关闭信号后，必须停止领取新任务。
- 长时间任务必须具备幂等、断点续跑或可补偿能力，不能只依赖锁保证正确性。

### 并发控制
- DKit 可以通过数据库记录限制某个资源的并发执行数量；当并发控制成为热点时，也可以演进到 Redis zset 等专用实现。
- 使用事务数据库实现时，可以通过 token 表、唯一约束和过期时间表达占用名额。
- 每个 token 必须有唯一标识和 ttl，避免执行方异常退出后永久占用名额。
- 释放 token 时必须校验 token 标识，禁止释放其他执行方的名额。
- 达到并发上限时，必须返回可判断的 busy 结果。

## 数据模型建议
- 协作表应按能力拆分，例如 lock、leader、heartbeat、id_node、worker_state、outbox。
- 所有协作表都应包含创建时间、更新时间或过期时间，便于排查与清理。
- 临时协作状态必须建立过期字段索引，避免历史数据无限增长。
- `resource key`、`node key`、`isolation key` 等字段长度必须受控，避免索引膨胀。
- 对热点资源，应评估分片、拆 key、降低竞争频率或迁移专用组件。
- 表结构属于实现细节，业务代码不得直接读写协作表。

## 可靠性要求
- DKit 实现必须清晰定义“获得资源”“未获得资源”“后端错误”“状态未知”的差异。
- 所有写入都必须考虑重复执行，尤其是锁获取、leader 续约、心跳上报、token 释放和 outbox 投递。
- 所有 lease 都必须设置过期时间，并根据业务恢复窗口配置 ttl。
- 所有抢占操作都必须基于条件写或事务，禁止先读后无条件写。
- 所有释放操作都必须校验持有者身份，禁止误删其他节点的新状态。
- 对外部副作用敏感的场景，应结合幂等键、fencing token 或事务状态机，不能只依赖锁。

## 可观测性
- DKit 应记录关键状态变化日志，包括获得锁、释放锁失败、leader 变更、续约失败、心跳失败、节点号分配失败。
- 日志应包含 `trace_id`、`request_id`、`resource_key`、`node_key`、`isolation_key`、`ttl`、`attempt` 与错误原因。
- DKit 应提供基础指标，包括锁获取耗时、锁竞争失败次数、leader 切换次数、心跳失败次数、ID 生成失败次数、后端存储错误次数。
- DKit 应避免在正常竞争失败场景输出大量 error 日志，防止噪音掩盖真正故障。
- DKit 的协作状态应支持查询或调试，方便定位当前 leader、存活节点、被占用锁和异常 outbox 事件。

## 适用场景
- 单实例后台任务互斥执行。
- 低频管理操作的跨节点互斥。
- 中小规模业务的趋势递增 ID 生成。
- 轻量 leader election，例如定时扫描、补偿任务、缓存预热、报表聚合。
- 需要把业务状态和异步事件写入放在同一事务边界内的 Outbox 场景。
- 需要在不引入新基础设施的情况下快速补齐分布式协作能力的演进早期系统。

## 不适用场景
- 高 QPS、低延迟、强竞争的锁服务。
- 对 failover 时间有极低要求的核心链路。
- 跨地域、跨机房强一致协调。
- 需要严格线性一致读写的协调服务。
- 数据库已经成为系统瓶颈，且协作写入会明显放大热点。
- 无法接受数据库主从切换、事务隔离或时钟精度带来误差的场景。

## 演进路径
- 初始阶段，使用事务数据库实现 DKit 原语，优先获得统一接口和明确语义。
- 业务增长后，监控锁竞争、协作表写入量、leader 切换频率、心跳失败率和数据库负载。
- 当事务数据库不再适合作为协作后端时，按能力替换底层实现，而不是修改业务调用方。
- 可先迁移热点能力，例如把高竞争锁迁移到 Redis，把强一致选主迁移到 etcd。
- 迁移期间应支持灰度切换、双写校验、按 `isolation key` 分批切换或只读校验。
- 迁移完成后，应清理旧协作状态，并保留必要审计记录。

## 与 patterns 规范的关系
- `patterns/spec.md` 定义跨语言、实现中立的标准实践。
- DKit 是这些标准实践在工程实现上的一种推荐组织方式。
- DKit 文档可以描述接口设计、存储模型和实现取舍，但不得反向要求规范绑定某一种数据库或某一个 Go 实现。
- 具体语言实现应以 patterns 规范为上游约束，并以 DKit 思想作为可选实现参考。

## 示例流程

### 基于数据库锁执行互斥任务
- Worker 使用任务名作为 `resource key` 创建分布式锁。
- 锁记录包含 `resource_key`、`holder_id`、`expires` 与可选 `fencing_token`。
- Worker 获取锁成功后开始扫描任务，并在 context deadline 或锁 ttl 内完成一个批次。
- Worker 完成后按 `holder_id` 和 `expires` 条件释放锁。
- 如果 Worker 异常退出，锁记录会在 ttl 到期后允许其他节点抢占。

### 基于数据库选主执行定时补偿
- 每个节点使用稳定的 `node key` 参与同一个 `isolation key` 下的 leader 竞选。
- leader 记录包含 `leader_key`、`node_key`、`isolation_key` 与 `expires`。
- leader 周期性续约，续约成功后继续执行补偿任务。
- leader 续约失败时，立即停止领取新任务并切换为 follower。
- follower 观察到 leader 过期后，通过条件更新或唯一插入参与竞选。

### 基于 Outbox 保证事件投递
- 业务服务在本地事务中同时写入业务数据和 outbox 事件。
- DKit Worker 通过分布式锁或选主保证同一分区同一时刻只有一个投递者。
- Worker 投递事件后更新事件状态。
- 投递失败时记录错误、增加重试次数，并按退避策略设置下一次投递时间。
- 消费方使用幂等键处理重复事件。
