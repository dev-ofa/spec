## patterns

### 状态
Draft

### 目标
- 本规范定义业务系统中常见工程模式的标准实践，包括 CRUD、唯一 ID、分布式锁、选主、心跳、异步 Worker 与分布式事务。
- 本规范强调演进式架构：在满足业务可靠性与容量要求的前提下， **应当** 优先复用已有事务数据库和业务基础设施，避免为了单一功能过早引入额外分布式组件。
- 当事务数据库、缓存或本地实现无法满足容量、可用性、时延或失效恢复要求时，系统 **应当** 支持平滑演进到专用组件或独立实现。

### 适用范围
- CRUD
- 唯一 ID
- 分布式锁
- 选主
- 心跳
- 异步 Worker
- 并发控制
- 分布式事务

### 非目标
- 本规范只定义行为语义与工程约束，不强制具体语言、框架、存储引擎或第三方组件。

### 设计原则
- 分布式能力 **必须** 服务于业务一致性、可用性与工程复杂度的平衡， **不应** 以“组件更多”作为架构先进性的判断标准。
- 对于中小规模业务场景，唯一 ID、分布式锁、选主与心跳 **可以** 复用已有事务数据库实现，以降低部署、运维与故障排查成本。
- 复用事务数据库实现分布式能力时， **必须** 显式评估数据库容量、事务隔离级别、唯一约束、时间精度、过期清理与故障恢复语义。
- 实现 **必须** 把能力抽象为稳定接口，业务代码 **不得** 直接依赖底层存储表结构、集合结构或临时键格式。
- 实现 **必须** 支持替换底层后端；当数据库实现不再满足要求时， **应当** 能迁移到 Redis、ZooKeeper、etcd、专用 ID 服务或消息系统等实现。
- 所有涉及等待、重试、轮询、抢占、心跳与事务提交的操作都 **必须** 支持 timeout 或 context cancellation， **禁止** 无界等待。
- 所有关键状态变化 **必须** 记录日志，并 **应当** 携带 trace_id、request_id、node_key、resource_key 等可定位字段。

### 术语

#### resource key
- 标识某个分布式资源的稳定字符串，例如锁 key、选主 key、并发控制 key 或事务分支 key。
- resource key **必须** 在业务语义内唯一，且 **应当** 避免直接拼接未校验的用户输入。

#### node key
- 标识参与选主、心跳或分布式协作的单个运行节点。
- node key **必须** 在同一隔离域内唯一，推荐由应用名、环境、实例 ID 或机器信息组合生成。

#### isolation key
- 标识一组彼此隔离的分布式协作域。
- 同一组件需要支持多租户、多业务线或多任务组时， **必须** 使用 isolation key 隔离选主、心跳与锁语义。

#### ttl
- 表示某个协作状态的最长有效期，例如锁持有时间、leader 租约时间、心跳存活时间或并发 token 有效期。
- ttl **必须** 大于一次正常操作的预期最长耗时，并 **应当** 小于业务可接受的故障恢复窗口。

#### lease
- 基于 ttl 的临时持有权。
- lease 到期后，其他节点 **可以** 按照规范重新竞争资源；原持有者 **不得** 假设自己仍然拥有资源。

#### fencing token
- 单调递增或可比较的令牌，用于防止旧持有者在 lease 失效后继续写入资源。
- 对强一致写入或外部副作用敏感的场景， **应当** 使用 fencing token 或等价机制。

### CRUD
- 资源以名词复数形式命名
- Create 与 Update **必须** 返回统一 Wrapper
- Delete 建议返回被删除资源的 id

### 唯一 ID

#### 目标
- 唯一 ID **必须** 保证业务定义范围内全局唯一。
- 作为主键或高频写入索引键使用的唯一 ID **应当** 具备趋势递增特性，以降低数据库索引写入抖动、页分裂、随机写入放大或 compaction 压力。
- 唯一 ID **必须** 支持多节点并发生成。
- 对外暴露的 ID 推荐使用字符串，避免不同语言、浏览器或 JSON number 精度差异导致截断。
- 主键 ID 的存储排序语义与对外传输语义 **可以** 不同； **不得** 为了让前端安全传输大整数，牺牲数据库中的主键排序语义。

#### 生成策略
- 实现 **可以** 使用雪花算法、数据库序列、号段、ULID、UUIDv7、唯一约束竞争或专用 ID 服务。
- 使用雪花算法或同等方案时， **必须** 定义时间位、节点位、序列位以及时钟回拨处理策略。
- 使用数据库序列或号段时， **必须** 定义号段分配、耗尽、回收与并发竞争失败时的处理策略。
- 使用 ULID、UUIDv7 或同类时间有序字符串 ID 时， **必须** 确认其规范字符串形式的字典序与期望时间序一致。
- 使用普通 UUIDv4 或其他随机 ID 作为主键时， **应当** 评估随机写入对索引局部性、写入成本和存储碎片的影响；高写入主表 **不应** 默认使用完全随机主键。
- 节点号 **可以** 通过配置静态分配，也 **可以** 通过事务数据库或中心化存储竞争式分配。
- 竞争式分配节点号时， **必须** 设置租约或过期时间，避免节点异常退出后永久占用。
- 使用数据库唯一约束生成 ID 或机器号时， **必须** 处理重复键冲突，并在有限次数或有限时间内失败。

#### 存储类型与对外类型
- 如果 ID 数值可能超过 JavaScript `Number.MAX_SAFE_INTEGER` 或其他调用方安全整数范围，API、消息、日志中的对外 ID 字段 **应当** 使用字符串。
- 数据库存储层 **可以** 使用数值型 ID，以保持数值排序、索引局部性和范围查询语义；对外序列化时再以字符串表达。
- 当语言或序列化框架支持自定义类型时， **可以** 提供“数据库按数值序列化、JSON/API 按字符串序列化”的 ID 类型，避免在每个接口返回前手工转换；该模式要求所有持久化编解码路径都正确识别该类型，接入成本高于普通字符串 ID。
- 当 **可以** 自由选择 ID 字符串格式时，优先选择固定宽度、字典序等于生成序的字符串编码，以减少数据库/API 边界的类型转换和自定义 codec 依赖。
- 如果数据库中使用字符串存储雪花算法等数值型 ID， **必须** 确认字符串编码的字典序与数值序一致；普通十进制字符串只有在固定宽度时才满足该条件。
- 对数值型 ID 转字符串后直接存储的实现， **不得** 假设其长度在系统完整生命周期内固定；长度跨越 10 的幂边界时，普通字符串字典序会偏离数值序。
- 如果 **必须** 用字符串存储数值型 ID 且依赖排序或范围查询， **应当** 使用固定宽度编码，例如左补零十进制字符串，或使用天然可按字典序排序的 ID 编码。
- 如果通过调整雪花算法 epoch 让新生成的十进制字符串提前进入目标位数区间，epoch **必须** 作为跨语言、跨服务、跨环境的固定兼容性常量；上线后 **不得** 随意变更，也 **不得** 让不同 epoch 的生成器同时服务同一 ID 空间。
- 固定宽度排序编码不一定适合作为对外展示 ID；当展示可读性和存储排序性冲突时， **应当** 拆分对外 ID 与内部排序键。

#### 排序键与 Feed Cursor
- 主键 ID 的趋势递增性有助于写入局部性，但不等价于适合直接作为 Feed/Cursor 锚点。
- 使用主键 ID 作为 Feed/Cursor 字段时， **必须** 确认其数据库比较语义与期望的时间序或生成序一致。
- 当主键 ID 的对外表达不适合排序，或未来可能因编码长度变化破坏字典序时，**应当** 单独定义稳定排序键，例如数值型 ID、固定宽度 `id_sort_key`、`feed_cursor`、`seq`、ULID 或 UUIDv7。
- Feed/Cursor 的排序键 **应当** 优先选择单字段、稳定、唯一或可与唯一字段组合形成稳定顺序的字段； **不应** 把普通页码或 offset 包装成 cursor。
- 对大流量 feed，不推荐允许调用方任意传入复杂排序；排序和 cursor 定义 **应当** 由实体或业务接口显式声明。

#### 时钟与容量
- 依赖本地时钟的实现 **必须** 检测时钟回拨。
- 对轻微时钟回拨， **可以** 选择等待、切换备用序列或进入降级模式；对超过阈值的回拨 **必须** 失败或阻止启动。
- 实现 **必须** 明确单节点每单位时间的最大生成能力，并在达到上限时阻塞、失败或等待下一时间窗口。
- ID 生成失败 **不得** 静默返回空值、零值或可能冲突的值。

#### 可观测性
- ID 生成失败 **必须** 记录错误日志。
- 实现 **应当** 记录节点号分配失败、时钟回拨、序列耗尽与后端存储异常。
- 关键业务可记录 ID 生成耗时与失败率指标。

### 选主
- 选主 **必须** 具备主从切换与主失效自动恢复能力。
- 选主 **必须** 暴露当前节点是否为 leader 的只读查询接口。
- 选主 **应当** 暴露当前 leader 的只读查询接口；当无法可靠获取当前 leader 时， **必须** 返回未知状态而不是伪造结果。
- 选主 **必须** 基于 node key 区分参与节点。
- 选主 **应当** 支持 isolation key，以便同一套基础设施承载多组独立选主。
- leader 身份 **必须** 有 lease 或等价过期机制， **禁止** 永久 leader。
- leader **必须** 定期续约；续约失败时，当前节点 **必须** 主动放弃 leader 身份。
- follower **必须** 能在 leader 失效后重新竞选。
- 选主状态变更 **必须** 记录日志，至少包含 node_key、is_leader、isolation_key 与变更原因。

#### 竞选规则
- 同一 isolation key 下，同一时刻最多只能有一个有效 leader。
- 竞选 **必须** 通过原子条件写、唯一约束、事务或等价 CAS 机制完成。
- 抢占过期 leader 时， **必须** 校验原 leader 的过期时间或版本，避免并发覆盖新 leader。
- 实现 **应当** 支持 CanElect 或等价机制，让节点在本地健康检查失败、依赖不可用或人工摘除时拒绝参选。
- 初次启动时，组件 **应当** 在完成一次竞选或确认无法竞选后再对外暴露确定状态。

#### 失效窗口
- 选主的不健康判定时间 **必须** 可配置。
- 竞选与续约间隔 **应当** 小于不健康判定时间，推荐不超过其二分之一。
- 不健康判定时间 **应当** 大于一次正常续约操作的超时、调度抖动与存储延迟之和。
- 对失效恢复要求高的场景， **不应** 仅依赖事务数据库轮询实现， **应当** 评估 etcd、ZooKeeper、Redis 或专用协调服务。

### 心跳
- 心跳用于描述节点存活状态，不等同于选主；系统 **可以** 只启用心跳，也 **可以** 将心跳与选主组合使用。
- 心跳 **必须** 包含 node key、isolation key 与 expires 或等价过期字段。
- 心跳写入 **必须** 是幂等的；同一节点重复上报 **应当** 更新存活时间，而不是产生多个存活记录。
- 心跳 **必须** 设置 ttl 或过期时间， **禁止** 永久存活记录。
- 查询存活节点时， **必须** 过滤已过期节点。
- 节点正常关闭时， **应当** 尽力删除或注销自己的心跳记录；异常退出时 **必须** 依赖过期机制自动恢复。
- 心跳失败 **必须** 记录日志，但短暂失败 **不应** 立即导致进程退出。
- 心跳间隔 **应当** 小于存活 ttl，推荐不超过 ttl 的二分之一。
- 心跳操作 **必须** 设置超时， **禁止** 因为心跳阻塞影响主业务流程。

### 分布式锁

#### 目标
- 分布式锁用于保护跨进程、跨实例的临界区。
- 分布式锁只能降低并发冲突概率， **不应** 作为替代业务幂等、唯一约束或事务一致性的唯一手段。
- 分布式锁 **必须** 支持 Lock、TryLock 与 Unlock 或等价语义。
- Lock 表示在有限等待时间内尝试获取锁；TryLock 表示立即或短时间尝试获取锁， **不得** 无限等待。
- Unlock 只能释放当前持有者持有的锁。

#### 锁语义
- 锁 **必须** 绑定 resource key。
- 锁 **必须** 设置 ttl， **禁止** 无过期时间的分布式锁。
- 获取锁时 **必须** 使用原子创建、唯一约束、条件更新、CAS 或等价机制。
- 抢占过期锁时， **必须** 校验原锁的过期时间、版本或持有者标识，避免误删或覆盖新锁。
- 解锁时 **必须** 校验持有者标识、版本、过期时间或 fencing token， **禁止** 无条件删除同名锁。
- 锁过期后，原持有者 **必须** 视为失去锁；如果业务操作可能超过 ttl， **必须** 续约、拆分任务或使用更长 ttl。
- 支持可重入锁时， **必须** 显式传入 reentrant identity，且 **必须** 定义同一 identity 的重入计数或重入释放规则。
- 不支持可重入锁的实现 **必须** 明确拒绝重入， **不得** 产生不确定行为。

#### 等待与重试
- Lock **必须** 支持最大等待时间或继承调用方 timeout quota。
- 自旋等待 **必须** 设置间隔，并 **应当** 附加 jitter，避免大量实例同时竞争造成惊群。
- 获取锁失败 **应当** 返回可判断的错误或布尔结果，业务方 **不得** 通过解析错误字符串判断是否获得锁。
- 操作完成后 **必须** 释放锁；释放失败 **必须** 作为错误返回或记录， **不得** 静默吞掉。

#### 适用边界
- 分布式锁适用于低频临界区、后台任务互斥、轻量资源保护与管理面操作。
- 高吞吐数据写入 **应当** 优先使用唯一约束、乐观锁、消息串行化、分区调度或专用协调组件。
- 对强一致外部副作用敏感的场景， **应当** 结合 fencing token、幂等键或事务状态机。

### 异步 Worker
- 任务 **必须** 具备幂等性设计
- 失败任务 **必须** 支持重试与死信
- 任务处理 **必须** 记录开始与结束日志
- 需要单实例执行的 Worker **可以** 使用分布式锁或选主实现互斥。
- Worker 获取互斥执行权后， **必须** 在每次执行前确认自己仍持有有效 lease 或 leader 身份。
- Worker 退出、失去锁、失去 leader 身份或 context canceled 时， **必须** 尽快停止领取新任务。
- 长时间任务 **必须** 支持分段提交、断点续跑或幂等重放。

### 并发控制
- 并发控制用于限制同一资源或业务动作的并发执行数量。
- 并发控制 **必须** 定义 max_concurrent，且 **必须** 在配置缺失或非法时失败。
- 并发 token **必须** 具备 ttl，避免执行方异常退出后永久占用并发名额。
- 释放 token 时 **必须** 校验 token 标识， **禁止** 释放其他执行方的名额。
- 达到并发上限时， **必须** 返回可判断的 busy 错误或明确的拒绝结果。
- 并发控制配置 **应当** 支持动态更新，但更新过程 **不得** 破坏已发放 token 的释放语义。

### 分布式事务

#### 目标
- 分布式事务用于协调多个本地事务、外部系统调用或异步消息之间的一致性。
- 业务 **应当** 优先使用本地事务保证单库内一致性， **不应** 为了简单单库写入引入分布式事务。
- 跨资源一致性 **应当** 优先评估是否 **可以** 通过幂等、最终一致、补偿、Outbox、Saga 或 TCC 建模。
- 只有在业务确实要求跨资源原子提交，且底层资源支持相应协议时，才 **应当** 使用强一致分布式事务。

#### 本地事务优先
- 单个事务数据库内的多表写入 **必须** 优先使用本地事务。
- 与主业务数据强相关的状态、去重记录、任务表、Outbox 事件与轻量协作记录 **可以** 复用同一个事务数据库。
- 将协作状态放入本地事务时， **必须** 确保状态变更与业务数据变更在同一事务中提交或回滚。
- 复用事务数据库实现协作能力时， **必须** 避免长事务、热点行、全表扫描与无限增长的历史记录。

#### Outbox
- 业务写入数据库并发布消息时，推荐使用 Outbox 模式。
- 业务数据与 outbox 事件 **必须** 在同一个本地事务中写入。
- 事件投递 **必须** 支持至少一次投递，消费者 **必须** 幂等。
- outbox 事件 **必须** 有状态字段、重试次数、下一次投递时间与错误信息。
- 投递失败 **必须** 支持重试；超过阈值后 **必须** 进入死信或人工处理流程。

#### Saga
- 多步骤跨服务写入 **可以** 使用 Saga 模式。
- Saga 的每个步骤 **必须** 具备明确的正向动作、补偿动作与幂等键。
- 补偿动作 **必须** 允许重复执行，并能处理正向动作未成功、部分成功或状态未知的情况。
- Saga 编排状态 **必须** 持久化， **禁止** 仅依赖进程内内存保存。
- Saga 失败后 **必须** 能够查询当前步骤、失败原因与可恢复动作。

#### TCC
- 对资源预留语义明确的场景， **可以** 使用 Try-Confirm-Cancel 模式。
- Try 阶段 **必须** 完成资源检查与预留， **不得** 直接提交不可取消的最终副作用。
- Confirm 与 Cancel **必须** 幂等。
- Confirm 与 Cancel **必须** 能处理空回滚、悬挂与重复请求。
- TCC 的预留资源 **必须** 有过期时间或超时取消机制。

#### **禁止** 事项
- **禁止** 在无幂等键的情况下对写操作进行自动重试。
- **禁止** 在事务中执行不可控耗时的远程调用。
- **禁止** 用长时间持有分布式锁来模拟跨服务事务。
- **禁止** 依赖进程内状态作为分布式事务的唯一事实来源。
- **禁止** 吞掉补偿失败、消息投递失败或事务状态推进失败。

### 演进策略
- 初始阶段 **可以** 优先选择本地事务数据库实现轻量分布式能力，以降低系统复杂度。
- 当出现明显热点、数据库写入压力过高、锁竞争严重、恢复窗口不满足要求或跨地域部署需求时， **应当** 评估迁移到专用组件。
- 迁移底层实现时，业务接口语义 **必须** 保持稳定。
- 迁移过程中 **应当** 支持双写校验、灰度切换或按 isolation key 分批切换。
- 底层实现切换完成后， **应当** 清理旧协作状态，避免过期数据影响后续判断。

### **禁止** 事项
- **禁止** 无 ttl 的锁、leader、心跳、token 或临时协作状态。
- **禁止** 无 context、无 timeout 或无最大等待时间的分布式协作操作。
- **禁止** 把分布式锁作为数据唯一性、业务幂等或事务一致性的唯一保障。
- **禁止** 业务代码直接依赖协作表结构、临时键格式或第三方组件命令。
- **禁止** 在无法判断成功与否的写操作上默认自动重试。
- **禁止** 用引入新组件替代对业务一致性模型的设计。

### 示例

#### 示例一：复用事务数据库生成雪花节点号
- 应用启动时，通过事务数据库唯一约束竞争一个可用节点号。
- 节点号记录带有过期时间，异常退出后 **可以** 被其他节点重新竞争。
- 应用获得节点号后，用雪花算法在本地生成趋势递增 ID。
- 当数据库竞争失败或节点号池耗尽时，应用 **必须** 失败或降级， **不得** 生成可能冲突的 ID。

#### 示例二：基于事务数据库的轻量分布式锁
- 获取锁时，对 resource key 执行唯一插入；如果记录已存在，则检查是否过期。
- 抢占过期锁时，通过条件更新校验旧 expires，避免覆盖其他节点刚获得的新锁。
- 执行业务临界区时， **必须** 受 context deadline 与锁 ttl 共同约束。
- 解锁时，通过持有者标识、版本或 expires 条件删除，避免误删他人的锁。

#### 示例三：选主与心跳组合
- 每个节点定期写入自己的心跳记录，并设置 expires。
- 所有节点基于同一个 isolation key 竞争 leader 记录。
- leader 定期续约 leader lease；续约失败时立即放弃 leader 身份。
- follower 发现 leader lease 过期后 **可以** 发起竞选。
- 查询存活节点时，只返回心跳未过期的节点。

#### 示例四：本地事务加 Outbox
- 订单服务在同一个本地事务内写入订单状态与 outbox 事件。
- 后台 Worker 扫描 outbox 表，将事件投递到消息系统。
- 投递成功后更新 outbox 状态；投递失败则记录错误并按退避策略重试。
- 消费方使用幂等键去重，允许事件至少一次投递。
