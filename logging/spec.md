## logging

### 状态
Draft

### 目标
- 统一请求生命周期日志的最小记录要求与推荐字段。
- 支撑基于 `trace_id`、`request_id` 的排障、审计与问题定位。

### 适用范围
- 服务入口处理一次请求或一次 RPC 调用时产生的生命周期日志。
- 与请求结果、耗时和错误摘要相关的结构化日志字段。

### 非目标
- 不限制具体日志库、采集管道、存储平台或检索系统。
- 不覆盖业务自定义埋点、审计平台或指标系统的全部设计。

### 请求生命周期日志

#### **必须**
- 服务 **必须** 明确定义请求生命周期日志的记录边界
- 每个进入该边界的请求 **必须** 记录一条开始日志与一条结束日志
- 日志 **必须** 包含 trace_id 与 request_id
- 链路上下文、请求结果和错误摘要 **必须** 使用结构化字段记录， **不得** 只拼接在 message 中
- 如果认证拒绝、路由未命中、前置处理失败或限流等请求没有进入该边界， **必须** 由对应处理层记录独立的拒绝或失败日志，并携带 `trace_id`、`request_id`、`method`、`path`、`status_code` 与错误摘要

#### 记录边界
- 请求生命周期日志 **可以** 记录在服务入口后的统一访问层，也 **可以** 记录在统一接口处理层
- 选择服务入口后的统一访问层时，生命周期日志表示更完整的服务内请求处理周期；请求参数与响应参数 **可以** 使用独立日志记录，并通过 `trace_id` 与 `request_id` 关联
- 选择统一接口处理层时，生命周期日志表示接口业务处理周期；该模式 **可以** 将链路上下文、请求参数、响应参数、结果和耗时收敛到接口处理相关日志中，但 **必须** 明确不覆盖的前置阶段，并为前置拒绝或失败提供独立日志
- 同一服务内 **不得** 同时记录两套语义相同的请求生命周期日志；如果存在多层日志， **必须** 使用不同事件名区分生命周期日志、参数诊断日志和错误主记录

#### 推荐字段
- method：请求方法或 RPC 名称
- path：HTTP 路径或服务名
- status_code：协议层状态码
- code：业务码
- duration_ms：请求耗时
- error：错误摘要

#### 开始日志
- 开始日志 **应当** 记录所定义生命周期边界入口的链路上下文快照
- 链路上下文快照 **应当** 记录以下标准字段中已解析出的值：
  - trace_id
  - request_id
  - operator
  - tenant_id
  - app_id
  - locale
  - remaining_timeout_ms
- `operator`、`tenant_id`、`app_id`、`locale`、`remaining_timeout_ms` 的语义与传播规则遵循 `tracing` 与 `resilience` 规范
- 开始日志 **不得** 记录完整原始 header；如果需要记录额外透传字段， **必须** 使用显式白名单

#### 结束日志
- 结束日志 **应当** 记录请求结果、耗时和错误摘要
- 结束日志 **不应** 重复记录完整链路上下文快照；除 `trace_id` 与 `request_id` 外，只 **应当** 补充与结果定位直接相关的字段
- 请求处理出现错误时， **应当** 由入口层、前置处理层或统一错误处理层生成一条错误主记录
- 错误主记录 **应当** 包含 `trace_id`、`request_id`、`method`、`path`、`status_code`、`code`、`duration_ms` 与错误摘要；是否包含堆栈取决于错误类别和脱敏要求
- 错误主记录 **不得** 替代请求结束日志；同一个错误也 **不得** 在中间层和入口层重复记录

### 请求与响应参数日志

- 服务 **可以** 记录请求参数和响应参数，用于问题定位、联调或审计
- 请求参数和响应参数 **可以** 与请求开始日志、请求结束日志合并记录，也 **可以** 作为独立的参数诊断日志记录
- 是否合并由实现方根据日志可读性、排障需求、参数体积和采集成本决定；规范不要求请求参数、响应参数与生命周期日志 **必须** 在同一条日志中
- 独立参数诊断日志 **必须** 携带 `trace_id` 与 `request_id`，并使用稳定事件名与生命周期日志区分
- 参数日志 **应当** 记录经过解析、裁剪和脱敏后的字段； **不得** 为了排障直接记录完整原始请求体、完整原始响应体或敏感凭证
- 默认情况下，参数日志 **应当** 支持关闭、采样或按接口白名单启用；高频接口、大响应接口和包含敏感数据的接口 **不应** 无条件记录完整参数
- 当请求参数或响应参数本身会影响路由、权限、租户隔离、计费、幂等或关键业务判断时， **可以** 将必要字段补充到生命周期日志或错误主记录中

### 请求内业务日志

- 请求处理过程中产生的业务日志 **应当** 携带 `trace_id` 与 `request_id`
- 普通业务日志 **不应** 重复记录完整链路上下文快照
- 普通业务日志 **应当** 优先保持 message 可读，并只补充当前事件定位所需的业务字段，例如 user_id、resource_id、conversation_id、task_id
- 当日志事件本身涉及身份解析、权限校验、租户隔离、灰度路由、计费、下游调用或跨协议传播时， **可以** 补充对应的 `operator`、`tenant_id`、`app_id`、`locale` 或白名单透传字段

### Header 与透传字段记录边界

- 日志 **不得** 对入站或出站 header 做全量 dump
- 标准链路字段 **应当** 先解析为规范语义字段，再按本规范记录；日志字段名 **应当** 使用 `trace_id`、`request_id`、`operator`、`tenant_id`、`app_id`、`locale`、`remaining_timeout_ms`， **不得** 直接依赖不同协议中的原始 header 名作为主要检索字段
- 业务自定义透传字段默认 **不得** 记录；只有当字段会影响路由、灰度、租户隔离、权限判断、审计、计费或关键排障时，才 **可以** 加入日志白名单
- 白名单字段 **必须** 有稳定名称、明确语义和脱敏策略
- 日志、trace、metrics、埋点、错误上报和审计记录 **不得** 输出原始 access token、refresh token、session cookie、query token、签名 URL、完整 credential、完整 Cookie header 或可直接复用的敏感值
- 如果为了排障需要记录凭证相关信息， **应当** 只记录 credential source、签发方、到期时间、摘要前缀或脱敏后的指纹；具体凭证约束遵循 `authentication` 与 `resource` 规范

### 级别建议
- 正常结束使用 INFO
- 预期内失败或业务失败通常使用 WARN；如果该失败是高频、无需排查且不影响系统健康的正常业务结果， **可以** 使用 INFO
- 非预期错误或系统错误使用 ERROR
- 错误分类、错误码分段、是否进入告警口径遵循 `error` 规范
