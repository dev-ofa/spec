## i18n

### 状态
Draft

### 目标
- 本规范定义跨语言、跨服务、跨客户端的国际化基础规则。
- 目标是让不同实现对 locale 选择、请求传播、资源回退、响应结构和地区化边界保持一致。
- 本规范优先约束会影响互操作和长期演进的规则，不规定具体框架、SDK 或目录布局。

### 适用范围
- 面向用户的客户端应用、服务端 API、服务间调用、异步任务和 AI 生成链路。
- 用户可见文案、错误表达、日期时间、数字、货币、内容资源和结构化报告等需要按语言或地区呈现的场景。
- 跨语言实现需要统一的 locale 语义字段、传递方式和 fallback 行为。

### 非目标
- 不维护具体产品的翻译词条、文案语气、内容策略或目标市场选择。
- 不规定某个前端、后端或 AI 框架的 i18n 库选型。
- 不把支付、合规、数据驻留、税务、风控等地区化决策简化为 locale 决策。
- 不规定业务项目内部的资源文件目录结构；项目可以按自身工程结构选择文件组织方式。

### 术语

| 术语 | 含义 |
| --- | --- |
| locale | 语言、地区和格式化习惯的组合标识，例如 `zh-CN`、`en-US`。 |
| language | 语言本身，例如 `zh`、`en`；不能完整表达地区、日期、货币等格式化差异。 |
| localization | 针对目标 locale 的文案、格式化和内容呈现。 |
| regionalization | 针对国家、地区、支付、合规、数据存储、客服资源等非纯语言因素的地区化治理。 |
| effective locale | 服务端在完成解析、归一化和 fallback 后，当前请求实际使用的 locale。 |

标准语义字段使用 `locale`，不得使用 `language` 表达完整国际化上下文。

### Locale 标识

- locale 值必须使用 BCP 47 风格的语言地区标识，例如 `zh-CN`、`en-US`。
- 业务系统必须声明自身支持的 locale 集合。
- 系统必须声明默认 locale。
- 收到未知、空值或不支持的 locale 时，必须回落到默认 locale 或项目声明的 fallback locale。
- 实现可以接受常见别名，例如 `zh`、`zh_CN`、`en`，但必须先归一化到支持集合中的标准值，再进入业务逻辑。

### Locale 决策优先级

服务端确定 effective locale 时，必须使用稳定且可解释的优先级。推荐优先级如下：

| 优先级 | 来源 | 规则 |
| --- | --- | --- |
| 1 | 用户显式选择 | 用户在产品内保存的语言偏好优先级最高。 |
| 2 | 当前请求显式参数 | 例如调试、WebSocket 握手或平台限制下传入的 `locale` 参数。 |
| 3 | `Accept-Language` | 用于首次访问、未登录用户或未保存偏好的请求。 |
| 4 | 客户端环境语言 | 只作为客户端初始化默认值，不应直接覆盖服务端已确定的用户偏好。 |
| 5 | 系统默认 locale | 前面来源均不可用时使用。 |

IP 地域、支付地区、账号注册地区或部署地区不得直接覆盖用户语言偏好。它们可以参与 regionalization 决策，但不能作为 locale 的最高优先级来源。

### 请求与服务间传播

客户端发起 HTTP 请求时，应使用标准 HTTP header 表达语言偏好：

```text
Accept-Language: zh-CN
```

服务端在入口处解析并归一化后，应得到 effective locale。服务间调用、异步任务、消息投递和跨协议调用应传播 effective locale，而不是原样传播未经解析的 `Accept-Language`。

标准服务间透传 header 为：

```text
OFA_PASS_LOCALE: zh-CN
```

传播规则：

- `OFA_PASS_LOCALE` 表达已经归一化后的 effective locale。
- 上游已经提供 `OFA_PASS_LOCALE` 时，下游服务应沿用，除非当前服务有明确的用户偏好变更或显式覆盖。
- 服务发起下游调用时，应继续透传当前请求上下文中的 `OFA_PASS_LOCALE`。
- HTTP 以外的协议应提供等价字段，字段语义仍为 `locale`。
- 查询参数 `locale` 只能用于 WebSocket 握手、调试、平台 header 受限或显式覆盖场景；普通 HTTP API 默认应优先使用 header。

`Accept-Language` 和 `OFA_PASS_LOCALE` 的语义不同：

| 字段 | 语义 |
| --- | --- |
| `Accept-Language` | 客户端语言偏好，可能包含多个候选值和权重。 |
| `OFA_PASS_LOCALE` | 服务端已决策并归一化后的 effective locale。 |

### 响应与协议稳定性

国际化不得改变业务协议结构。

- JSON 字段名、枚举值、状态值、错误码、资源 ID、业务 key 必须保持稳定，不随 locale 改变。
- 用户可见 message、标题、说明、按钮文案、格式化后的日期时间和金额可以随 locale 改变。
- 前端或下游服务不得把自然语言标题、段落、Markdown 层级或本地化文案作为业务事实解析来源。
- 需要被程序消费的评分、风险、建议、优先级、标签、分类等信息必须由稳定结构化字段承载。

错误响应应优先提供稳定错误码；用户可见错误文案按 effective locale 映射。服务不得把内部异常字符串直接作为用户可见本地化文案。

### 资源与 Fallback

所有用户可见内容资源都应具备 locale 维度。资源包括但不限于：

- UI 文案、表单提示、Toast、空状态和帮助说明。
- 错误 message、业务状态说明和通知模板。
- 题库、选项、画像解释、报告 section copy 和行动建议模板。
- Prompt、示例、fallback 话术和 AI 生成约束。
- 用户协议、隐私政策和同意展示文本。

资源查找必须具备确定性的 fallback 顺序。推荐顺序为：

1. 当前 effective locale 对应资源。
2. 当前 locale 的项目声明 fallback 资源。
3. 系统默认 locale 资源。
4. 明确的缺失资源占位或错误。

资源缺失不得静默返回错误语言的内容，除非该行为是项目明确声明的 fallback 规则。

### 格式化

日期、时间、数字、百分比和货币格式化必须接收 locale 或从请求上下文读取 effective locale。

- 日期和时间格式不得写死某一地区格式。
- 数字和百分比格式不得依赖运行环境默认 locale。
- 货币格式化必须同时持有 currency，不得只依赖 locale 推断币种。
- 输入、存储和计算应使用稳定结构化值；本地化格式只用于展示。

### AI 生成链路

AI 生成链路必须显式接收 effective locale。

- Prompt、系统变量、工具输入和报告生成约束应使用同一个 effective locale。
- 固定开场、fallback、示例、评分解释、报告 section copy 等属于本地化资源。
- AI 输出中需要被程序消费的信息必须使用结构化字段；Markdown 或自然语言文本只能作为展示内容。
- 当目标 locale 的 Prompt 或示例缺失时，必须按声明的 fallback 顺序处理，不得让不同语言资源随机混用。

### Regionalization 边界

locale 只决定语言和展示格式，不等同于地区化治理。

以下能力必须由独立的地区化、合规或业务配置控制：

- 支付渠道、币种、税务和账单描述。
- 隐私政策、用户协议、同意展示和数据授权。
- 数据存储地区、数据跨境、审计和监管要求。
- 客服入口、第三方平台账号、营销素材和地区资源。
- 未成年人保护、内容安全和风控策略。

系统可以同时使用 locale 和地区化配置，但不得只通过 locale 推导上述业务决策。
