## error

### 状态
Draft

### 目标
- 定义跨语言、跨工程类型通用的错误处理原则，包括错误分类、错误传播、上下文补充、记录与对外表达。
- 区分需要关注的非预期错误与预期内失败，降低重复记录、误告警、错误信息丢失和错误语义漂移的风险。
- 同时覆盖显式错误处理语言与集中式异常处理语言，使不同语言实现可以采用各自惯用方式表达同一套错误语义。

### 适用范围
- 服务端应用、任务处理器、SDK、CLI、本地工具、批处理脚本与基础库。
- HTTP/RPC 调用、数据库、缓存、消息队列、文件系统、第三方服务等系统边界处的错误处理。
- 需要在进程内、模块间、服务间或对外 API 中传递错误语义的场景。

### 非目标
- 不规定具体语言的错误库、异常框架、日志 SDK 或 metrics SDK。
- 不要求所有工程都定义错误码；错误码只在服务端 API、RPC、SDK 网关或需要跨进程稳定传递错误语义的场景中适用。
- 不替代 `api`、`logging`、`resilience` 与 `tracing` 规范；涉及响应结构、日志字段、超时重试与链路标识时，以对应规范为准。
- 不覆盖完整的用户提示文案规范、国际化规范或审计事件模型。

### 核心原则
- 错误必须能够被稳定分类，分类结果用于决定是否需要关注、是否告警、如何记录以及是否可以安全对外表达。
- 错误处理必须保留原始 cause 或等价异常链路，不得在包装、转换或返回时丢失根因。
- 错误上下文应在错误发生点或系统边界补充；普通中间层不应重复包装没有新增语义的错误。
- 同一次请求或任务中的同一个错误应尽量只生成一条主记录，避免多层重复记录导致排障噪声和指标膨胀。
- 顶层边界必须兜底处理所有错误和未捕获异常，避免错误逃逸到运行时默认处理逻辑。

### 错误处理范式

#### 显式错误处理
显式错误处理适用于 Go 等语言。调用方在收到错误返回值时，必须明确采取以下动作之一：
- 向上返回错误。
- 将错误转换为当前层语义下的错误类型。
- 根据错误类型执行业务分支、补偿、降级、重试或 fallback。
- 在当前入口层消化错误并生成响应、任务结果或退出状态。
- 在确认为不可恢复时触发 panic、fatal 或等价机制。

显式错误处理语言中，普通业务函数默认只负责补充必要上下文并返回错误。除非当前函数已经是入口层或确实需要就地处理，否则不应在每个错误判断点同时记录日志、metrics 或 event。

#### 集中式异常处理
集中式异常处理适用于 Java、C#、Python 等异常优先语言。业务代码可以抛出异常，由框架、中间件、入口函数或任务调度器统一捕获并处理。

中间层只有在需要执行明确处理动作时才应捕获异常。捕获后仅记录再抛出，通常会造成重复日志，应避免。

集中式异常处理语言中，应使用可识别的异常类型、错误基类或错误类别承载错误语义，不应依赖异常 message 的字符串内容判断业务逻辑。

### 错误分类

#### 非预期错误
非预期错误指系统运行中不应发生、通常需要开发者或运维关注的错误。

典型场景包括：
- 未处理的程序异常。
- 数据库、缓存、消息队列、文件系统或下游服务不可用。
- 下游服务超时、连接失败、返回非预期协议状态或响应格式不合法。
- 配置缺失、依赖初始化失败或关键运行环境不满足。
- 数据不一致、状态机进入不可能状态或内部不变量被破坏。

处理要求：
- 必须保留足够定位问题的上下文。
- 应进入系统错误观测口径。
- 服务端场景下通常应记录为 `ERROR`。
- 对外响应不得暴露 SQL、堆栈、密钥、内部 URL、内部服务拓扑等敏感信息。

#### 预期内失败
预期内失败指由输入、权限、业务规则、资源状态或用户操作导致的可预期结果，通常不需要系统告警。

典型场景包括：
- 参数校验失败。
- 前置条件不满足。
- 权限、额度、频控、状态限制导致的拒绝。
- 调用方可理解并可修正的业务提示。
- 接口语义中明确允许的资源不存在、资源冲突、幂等重复或版本冲突。

处理要求：
- 必须有稳定、可识别的错误类别或错误类型。
- 默认不应进入系统错误告警口径。
- 服务端场景下通常记录为 `WARN` 或 `INFO`，具体级别取决于是否需要排查。
- 对外 message 可以面向调用方表达原因，但仍不得泄露内部敏感信息。

### 错误类型设计

工程应定义稳定的错误类型，而不是只返回字符串或只抛出通用异常。错误类型应明确区分「原始错误」和「错误容器」。

#### 原始错误

原始错误是在某个语义边界内定义错误分类的错误，通常创建于错误发生点。模块边界需要重新解释底层错误时，也可以创建当前模块语义下的原始错误。

原始错误应表达：
- `message`：开发者可读的错误描述。
- `cause` / `source`：导致该原始错误的底层错误或异常；如果没有底层错误，可以为空。
- 稳定类型或稳定分类：例如 `validation`、`resource`、`internal`、`http_protocol`。

当工程需要跨进程、跨模块或对外稳定表达错误语义时，原始错误还应携带 `code`。`code` 用于唯一定位一类原始错误，并决定该错误属于预期内失败还是非预期错误。

服务端 API、RPC、SDK 网关或需要跨进程传递错误语义的场景中，推荐使用错误码：
- `code >= 20000` 表示预期内失败。
- `code < 20000` 表示非预期错误。
- `20000` 是默认预期内失败。
- `10000` 是默认非预期错误。

服务端 API 使用统一响应 Wrapper 表达应用层失败时，Wrapper 中的失败 `code` 应来自原始错误的 `code`。错误容器不得重新定义 `code`。

库、CLI、本地工具、批处理脚本等场景，如果错误只在进程内传播，通常只需要稳定错误类型和 cause 链路；如果基础库已经提供统一 code 体系，也可以使用 code 作为分类机制。

典型原始错误包括：
- 参数校验错误。
- 资源不存在、资源冲突、版本冲突。
- 内部状态错误。
- HTTP/RPC 协议响应不符合预期。
- 依赖初始化失败。

#### 原始错误与错误容器的选择

原始错误用于确定当前模块的错误语义，错误容器用于补充已有错误的传播上下文。

选择规则：
- 需要定义或改变错误分类、错误码、预期性、对外 message 或当前领域语义时，应创建当前模块的原始错误，并保留底层 cause。
- 已有错误分类对当前模块仍然成立，只补充 operation、target、request_id、resource、extra data、retryable 等上下文或处理标记时，应使用错误容器。
- 既不改变错误语义，也不能补充有效上下文时，应直接返回原错误。

典型选择包括：
- 调用语言基础库或第三方库解析输入失败，例如时间、数字、JSON、URL、配置文本解析失败。如果当前模块需要表达为参数错误、配置错误或协议错误，应创建当前模块的原始错误，并保留底层 cause。
- 数据库、缓存、存储或 SDK 返回资源不存在、唯一键冲突、版本冲突等底层错误时，如果这些状态是当前接口契约的一部分，应转换为当前模块的资源类原始错误；如果它们表示当前模块内部状态异常，应转换为当前模块的非预期原始错误。
- 调用下游服务或依赖失败，且错误语义仍是依赖调用失败时，应使用错误容器补充 target、operation、request_id 等上下文，不应重新定义错误码。
- 对已有错误增加可重试标记、结构化数据或排障上下文时，应使用错误容器，不应改变原始错误分类。
- 模块边界需要把下游错误解释为当前模块公开契约的一部分时，应在边界处转换为当前模块的原始错误；下游错误只作为 cause 保留。

#### 错误容器

错误容器是在错误传播链路中为已有错误添加上下文的包装层。错误容器承载 cause，并附加定位信息，但不代表新的错误根因。

错误容器不应定义新的 `code`。否则包装层会覆盖或污染原始错误的分类，使错误码失去“唯一定位一类原始错误”的含义。

错误容器应表达：
- `cause` / `source`：被包装的错误或异常。
- 上下文字段：例如 operation、target、request_id、resource、extra data、是否可安全重试等。

典型错误容器包括：
- Go 的 `fmt.Errorf("...: %w", err)`。
- 下游调用上下文包装，例如 `UpstreamError(target, operation, request_id, cause)`。
- 结构化补充数据包装，例如 `ExtraDataError(cause, data)`。
- 可重试标记包装，例如 `RetryableError(cause)`。

错误容器必须保留 cause 链路，并允许调用方继续识别链路中的原始错误类型、错误码或关键底层错误。

如果某个模块需要统一补充错误容器，应优先在模块入口层或调用边界统一包装，而不是在内部每个函数、每个错误分支分别包装。内部函数应尽量返回原始错误或局部语义明确的容器，入口层负责补充统一的 operation、target、request_id 等边界上下文。

禁止只通过错误字符串判断错误类型。实现应提供类型判断、错误码判断、错误类别判断或等价机制。

### 错误上下文

错误上下文必须在错误发生点或系统边界补充。

#### 错误发生点
当前代码明确产生错误时，应补充能直接定位该错误的上下文。

典型上下文包括：
- 参数名、非法值、期望格式或取值范围。
- 业务资源 ID、租户、操作者或关键业务维度。
- 当前状态、期望状态和状态转换动作。
- 校验失败原因和可修正提示。

#### 系统边界
调用非当前模块、非当前工程或外部依赖时，应在边界处包装错误。

典型上下文包括：
- HTTP/RPC 调用的 method、URL 或 RPC 名称、目标服务、协议状态、下游业务状态、request_id。
- 数据库或缓存操作的 operation、table/collection/key、关键资源标识。
- 消息处理的 topic、partition、offset、message_id、消费组。
- 文件或对象存储操作的 bucket、path、object_key、operation。

边界包装必须保留原始 cause。包装后的错误应仍可识别 timeout、canceled、not found、validation failed 等根因类别。

### 错误传播

普通业务层默认向上传播错误，不负责最终记录、告警或对外响应转换。

中间层只有在以下场景才应处理错误：
- 需要执行业务补偿、回滚或资源清理。
- 需要将依赖错误转换为当前领域错误。
- 需要根据错误类型执行降级、重试、fallback 或熔断判断。
- 需要识别错误类型并改变业务流程。
- 当前层是请求入口、任务入口、消费者 handler、命令行入口等顶层边界。

如果捕获错误后无法增加语义，也不执行处理动作，应直接传播原错误。

### 错误记录

同一次请求或任务中的同一个错误应尽量只记录一次主记录。主记录通常由入口层、框架中间件、任务调度器或统一错误处理器生成。

顶层记录应统一决定：
- 日志级别。
- 是否产生 metrics。
- 是否产生 event。
- 是否触发告警。
- 对外响应、任务结果或退出状态。

记录方式应服务于明确目标：
- `log` 用于排障、追溯和开发调试。
- `metrics` 用于趋势、SLO、错误率和告警。
- `event` 用于审计、安全事件或关键业务变更。

不应在每一层同时记录 log、metrics 和 event。确需多种记录方式时，应由统一处理器或框架封装完成，避免业务代码分散记录。

### 顶层处理

服务入口、任务入口、消费者 handler、CLI main 函数或等价顶层边界必须兜底处理错误和未捕获异常。

顶层处理器应根据工程类型完成适用动作：
- 将错误分类为非预期错误或预期内失败。
- 记录请求、任务或命令执行结果。
- 生成 metrics、event 或告警信号。
- 将错误转换为 API 响应、RPC 状态、任务失败原因或进程退出码。
- 对未知错误使用统一的非预期错误兜底。

服务端 API 场景下，错误到响应的映射应遵循 `api` 规范。应用层业务响应 wrapper 中的错误码分段以 `api` 规范为准。

CLI 场景下，预期内失败可以返回明确错误信息和非零退出码；非预期错误应保留调试信息的获取路径，例如日志文件、trace_id 或 verbose 模式。

批处理和异步任务场景下，错误处理结果应能表达可重试、不可重试、部分成功或需要人工介入等状态。

### 下游错误处理

调用第三方服务或内部下游服务时，应在当前工程语义下处理下游错误，使其可识别、可分类、可排障。处理方式可以是透传、使用错误容器补充上下文，或转换为当前模块的原始错误。

处理后应尽量保留：
- 下游服务名或稳定目标标识。
- 协议类型。
- method、RPC 名称或 operation。
- URL、资源名或对象标识。
- 下游 request_id。
- HTTP status、RPC status 或等价协议状态。
- 下游业务 code；仅当下游协议存在稳定 code 时适用。
- 原始错误 cause。

下游错误处理不得把所有错误都转换成不可识别的通用内部错误。调用方应能区分超时、取消、连接失败、协议失败、下游业务失败和响应解析失败等关键类别。

如果一个模块本身就是下游调用的统一入口，例如 HTTP client、RPC client、数据库 client 或 SDK client，推荐在该入口的统一出口补充下游调用容器。模块内部的 resolver、picker、request builder、response parser 等子函数通常不应重复包装同一种下游容器，避免上下文分散、重复包装和遗漏分支。

上游服务或模块不应无条件继承下游错误的预期性。下游返回的验证错误、资源错误或业务错误，对下游可能是预期内失败，但对上游可能表示内部参数组装错误、配置错误、依赖状态异常或代码缺陷。

下游返回可识别错误时应遵循：
- 如果下游错误已经是当前模块公开契约的一部分，且分类、错误码和 message 都适合直接暴露给当前调用方，可以透传，或仅使用错误容器补充调用上下文。
- 如果下游错误暴露的是当前模块内部调用参数、内部配置或内部状态问题，应转换为当前模块的非预期原始错误，并保留下游错误作为 cause。
- 如果下游错误由当前调用方输入直接触发，且当前模块契约也将其定义为输入错误，应转换为当前模块的预期原始错误，并保留下游错误作为 cause。
- 如果下游错误类型、错误码或协议语义不在当前模块已知契约内，不应直接透传其分类；通常应转换为当前模块的依赖失败、协议失败或内部失败语义，并保留 cause。

### panic / fatal

只有不可恢复且继续运行可能导致更严重问题时，才允许使用 panic、fatal 或等价机制。

允许场景包括：
- 启动期关键配置缺失。
- 必需依赖初始化失败。
- 程序进入不可能状态且无法安全恢复。

请求处理过程中的普通业务失败、参数错误、资源不存在、权限拒绝、下游失败不应使用 panic 表达。

入口层必须对可恢复的 panic 或未捕获异常建立兜底处理机制，并将其归类为非预期错误。

### 与其他规范的关系
- API 响应 wrapper 与传输层失败遵循 `api` 规范；应用层错误码分段与错误分类遵循本规范。
- 请求生命周期日志字段与日志级别建议遵循 `logging` 规范。
- 超时、重试、remaining timeout 传播与重试允许条件遵循 `resilience` 规范。
- `trace_id`、`request_id` 的定义与跨协议传播遵循 `_meta` 与 `tracing` 规范。
- 服务间调用目标标识、系统边界与发现方式遵循 `service` 规范。

### 禁止事项
- 禁止吞掉错误后继续执行。
- 禁止只返回字符串错误且无稳定类型、类别或等价识别机制。
- 禁止依赖错误字符串做业务判断。
- 禁止中间层重复记录同一个错误。
- 禁止在包装或转换错误时丢失原始 cause。
- 禁止把所有错误都包装成内部错误。
- 禁止把预期内失败默认纳入系统错误告警。
- 禁止把仅适用于服务端 API 的错误码要求强加给库、CLI、本地工具或批处理脚本。
- 禁止向外部响应泄露内部堆栈、SQL、密钥、内部服务地址等敏感信息。
