## service

### 状态
Draft

### 目标
- 本规范定义服务间调用与发现的统一约束，覆盖跨系统调用与系统内部调用。
- 目标是在不限制底层基础设施实现的前提下，统一系统边界表达、默认调用协议、服务发现抽象与调用方接入方式。
- 本规范强调“跨系统访问看入口，系统内寻址看发现”，避免系统边界模糊、调用方式失控与基础设施实现耦合。
- 本规范只定义跨语言统一的行为语义与抽象接口，不限制具体服务中心、服务网格、DNS 方案或 SDK 实现。
- 超时、重试与剩余超时传播遵循 `resilience` 规范；链路标识透传遵循 `tracing` 规范。
- 除非另有说明，本规范中的“必须”表示强制要求，“应”表示推荐要求，“可以”表示可选能力，“不得”表示显式禁止。

### 设计原则
- 所有服务间调用都必须有清晰、稳定且可治理的目标标识，不得依赖临时实例地址、人工维护 IP 列表或不可追踪的隐式路由。
- 跨系统调用与系统内部调用必须采用不同的寻址模型：前者通过稳定入口访问，后者通过服务发现完成实例寻址。
- 服务间调用默认必须采用 HTTP/HTTPS，以提升接口可读性、调试便利性、跨语言接入能力与治理一致性。
- 服务发现的底层实现可以多样化，但调用方侧必须面向统一抽象，而不是直接耦合某个服务中心产品。
- 灰度、路由、限流、熔断等治理能力可以纳入统一模型，但当前版本只定义基础抽象与扩展位，不强制复杂策略与算法。

### 术语

#### system
- system 是承载相对独立业务语义与责任边界的一组服务集合。
- 如果一次服务调用通过独立域名作为稳定入口完成，则该调用在技术上视为跨 system 调用。
- system 的业务边界可以由组织、产品或业务能力划分，但本规范中的技术判定以调用入口形式为准。

#### cross-system call
- cross-system call 指调用方通过目标 system 的稳定入口发起访问的服务调用。
- cross-system call 必须通过域名或等价的稳定入口标识访问目标 system，不得直接依赖目标 system 的内部实例地址。

#### intra-system call
- intra-system call 指同一 system 内部服务之间的调用。
- intra-system call 必须通过服务发现完成逻辑服务名到实例地址的解析，并允许在运行时按健康状态与治理规则选择目标实例。

#### stable entry
- stable entry 指某个 system 对外暴露的稳定访问入口。
- stable entry 默认使用域名表达，也可以由网关域名、负载均衡域名或其他稳定名称承载。
- stable entry 的目标是表达 system 边界与访问契约，而不是暴露内部实例拓扑。

#### logical service name
- logical service name 指在 service discovery 中使用的逻辑服务标识。
- logical service name 必须在其命名空间或隔离域内唯一，并保持稳定。
- 调用方必须面向 logical service name 编程，而不是写死单个实例地址。

#### service discovery
- service discovery 指调用方根据 logical service name 获取可用实例集合及其元数据的能力。
- service discovery 只解决“如何找到可调用实例”的问题，不等同于完整流量治理、身份认证或协议转换体系。

#### service registry
- service registry 指承载服务注册、健康状态、实例元数据与查询能力的基础设施组件。
- service registry 可以由 DNS、服务中心、控制面、服务网格或其组合实现。

#### caller-facing discovery protocol
- caller-facing discovery protocol 指调用方侧访问服务发现能力时所遵循的统一抽象接口。
- 该协议面向调用方 SDK、基础设施组件或运行时，不要求业务代码直接感知底层服务中心产品。
- 不同 service registry 的实现可以通过适配方式对齐该协议。

### 适用范围
- 本规范适用于所有服务间调用，包括跨 system 调用与 intra-system call。
- 浏览器到服务端、终端到服务端等终端接入流量，不属于本规范的主要约束对象；如与服务间调用共享同一入口，可按网关规范另行约定。
- 长连接、双向流、消息订阅与持续推送场景可以复用本规范的边界、寻址与发现原则，但协议细节可另行约定。

### 系统边界与调用方式

#### 边界表达
- cross-system call 必须通过目标 system 的 stable entry 发起，默认以域名作为访问标识。
- stable entry 必须稳定、可文档化、可审计，并不得直接暴露内部实例地址、Pod 名称或节点 IP。
- 同一 system 对外可以存在多个域名入口，但必须能够明确映射到统一的 system 边界与责任主体。

#### 跨系统调用
- 调用方访问其他 system 时，必须通过域名或等价稳定入口访问，不得直接使用对方的 logical service name 进行实例发现。
- 如果确有跨 system 直接发现实例的特化场景，必须由平台统一治理并显式约定，不得作为默认机制。
- cross-system call 的认证、授权、审计与限流策略必须绑定在 stable entry 或等价边界上实施。

#### 系统内部调用
- intra-system call 必须通过 service discovery 完成逻辑寻址与实例选择。
- intra-system call 不得依赖固定实例 IP、临时主机名或人工维护地址列表。
- 调用方在同一 system 内必须优先使用 logical service name，而不是复用对外域名入口作为内部高频调用路径。
- 系统内部可以通过 DNS、服务中心、Sidecar 或本地缓存解析实例；本规范不强制限定具体实现。

### 服务协议

#### 默认协议
- 服务间请求-响应式调用默认必须采用 HTTP/HTTPS；存在本章定义的例外场景时，可以采用其他协议。
- 默认采用 HTTP/HTTPS 的原因包括接口可读性更高、文档与调试成本更低、跨语言接入更直接，以及更容易与网关、观测与治理体系对齐。
- 对外暴露 HTTP 接口时，必须遵循 `api` 规范中的资源命名、资源表示与响应约束。

#### 例外协议
- 在存在明确特化需求时，可以使用 RPC 或其他协议。
- 允许使用 RPC 的典型场景包括显著的性能收益、流式响应、双向流通信、强类型契约要求或协议生态强依赖。
- 仅以团队偏好、历史习惯或“看起来更先进”为理由，不得作为引入 RPC 的充分依据。

#### 例外约束
- 采用 RPC 或其他非 HTTP 协议时，调用方与服务提供方仍必须满足可观测、可调试、可治理与可文档化要求。
- 采用 RPC 时，必须提供稳定的接口定义、错误语义说明、超时与重试约束，以及必要的调试或代理手段。
- 非 HTTP 协议的引入不得绕过 `tracing` 与 `resilience` 规范中的传播要求。

### 服务发现

#### 目标能力
- service discovery 必须至少提供逻辑服务名查询、健康实例筛选与实例元数据返回能力。
- service discovery 必须支持实例注册、实例注销、失效剔除或等价机制，确保调用方不会长期使用不可用实例。
- service discovery 必须支持命名空间、环境、地域或等价隔离维度，以避免不同隔离域的实例互相污染。

#### 调用方抽象
- 调用方必须通过 caller-facing discovery protocol 获取服务发现能力，不得直接耦合具体 service registry 的私有接口。
- caller-facing discovery protocol 必须支持按 logical service name 查询可用实例集合。
- 返回结果必须至少包含实例地址、端口、协议提示或等价连接信息，以及用于治理的基础元数据。
- 基础元数据必须支持携带版本、标签、可用区、权重或等价字段，以承载轻量治理能力。

#### 实例选择
- 调用方收到实例集合后，可以由 SDK、运行时、Sidecar 或平台代理层执行实例选择。
- 实例选择必须优先过滤不健康实例；是否采用随机、轮询、加权或其他策略不由本规范强制限定。
- 调用方可以缓存服务发现结果，但必须具备过期、刷新与失败兜底机制，避免长期使用陈旧实例信息。

#### 实现方式
- 在云原生环境中，可以优先使用 DNS 作为 service discovery 的基础能力。
- 当需要更丰富的实例元数据、灰度、动态路由或统一治理能力时，可以引入独立 service registry 或等价服务中心。
- 本规范不限制底层发现机制使用 DNS、注册中心、服务网格或混合方案，但上层抽象能力必须保持一致。

### 服务中心接入

#### 抽象边界
- 本规范统一的是 caller-facing discovery protocol 与抽象能力，不统一具体 service registry 产品。
- service registry 的实现可以自由选择，但如果要接入本规范体系，必须能够对调用方暴露一致的发现语义。
- 业务代码不得直接依赖某个服务中心的专有 SDK、专有模型或专有错误码。

#### 最小语义
- 对调用方暴露的服务发现语义必须至少包括：按逻辑服务名查询候选实例集合、返回实例元数据、表达服务不存在或无可用实例。
- 如果底层实现支持主动推送、长连订阅或本地 watch，可以作为增强能力；调用方抽象不得强依赖某一种实现机制。
- 不同实现对同一逻辑服务名的查询结果，在健康状态与隔离域一致的前提下，必须具有等价语义。

#### 调用方服务发现协议草图
- caller-facing discovery protocol 目前只定义抽象请求与响应语义，不强制规定必须使用 HTTP、gRPC、Unix Socket 或进程内函数调用。
- 无论采用何种传输方式，协议字段语义、返回结果解释与失败分类都必须保持一致。
- 第一版协议必须至少提供一个“按逻辑服务名解析候选实例集合”的查询动作；watch、推送、增量订阅等能力可以后续扩展。

#### 查询动作
- 查询动作的标准语义为：调用方根据 logical service name 与可选筛选条件，请求当前可用实例集合。
- 查询动作必须返回“可立即参与调用的实例视图”，而不是未过滤的原始注册数据。
- 如果底层实现无法保证强实时一致性，返回结果可以是最终一致视图，但必须明确携带生成时间或等价版本信息。

#### 请求字段

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| service_name | 是 | 目标 logical service name。必须是调用方实际用于寻址的稳定服务名。 |
| namespace | 是 | 服务所属命名空间、环境或等价隔离域。用于避免不同隔离域的同名服务混淆。 |
| label_selector | 否 | 标签选择表达式。用于表达调用方要求实例必须满足的硬过滤条件，语义应尽量对齐 Kubernetes label selector。 |
| preferred_label_selector | 否 | 偏好标签选择表达式。用于表达调用方优先选择的实例条件，语义应尽量对齐 Kubernetes label selector。 |
| resolve_mode | 否 | 实例解析模式。第一版可以支持 `healthy_only` 与 `all`；默认必须为 `healthy_only`。 |
| request_id | 否 | 本次发现请求的单跳标识。若当前调用链已存在 `request_id`，应沿用其语义。 |
| trace_id | 否 | 当前链路标识。若当前调用链已存在 `trace_id`，应沿用其语义。 |

#### 请求语义
- `service_name` 与 `namespace` 共同构成一次查询的最小定位键；二者缺失任一项时，请求必须失败。
- `label_selector` 用于表达硬过滤条件；如果没有实例满足条件，返回结果必须表达“无可用实例”，而不是自动降级忽略。
- `preferred_label_selector` 用于表达软偏好条件；如果没有实例满足偏好条件，实现可以回退到其他健康实例。
- `label_selector` 与 `preferred_label_selector` 的语义应尽量对齐 Kubernetes label selector；第一版至少应支持基于等值匹配的选择表达式。
- `resolve_mode=all` 只可用于诊断、控制面或平台内部场景；业务调用路径默认不得依赖非健康实例结果。
- 第一版协议中的单次查询结果必须能够表达当前调用方可用的完整候选实例视图，不得通过分页、游标或截断分页要求调用方多次请求后再自行拼装结果。

#### 简化服务发现标识符
- 为方便 CLI、诊断与人工运维场景，可以定义简化的服务发现标识符。
- 简化标识符的推荐格式为 `{logical_service_name}.{namespace}`。
- 在需要表达拓扑作用域时，可以扩展为 `{logical_service_name}.{namespace}.{zone}`。
- 三段式中的 `zone` 只表示查询作用域、优选拓扑或筛选条件，不得作为服务稳定身份的一部分。
- 当输入使用三段式简化标识符时，协议实现必须将其解释为：
  - `service_name = logical_service_name`
  - `namespace = namespace`
  - `preferred zone` 或等价筛选条件 = `zone`
- 协议实现不得要求调用方只能使用简化标识符；结构化字段 `service_name`、`namespace` 仍然是规范接口。

#### URL 中使用服务标识符
- 在 intra-system call 或明确受控的服务发现场景中，HTTP URL 的 host 部分可以使用服务标识符，而不必须是可直接由 DNS 解析的域名。
- 当 URL 的 host 使用服务标识符时，该标识符必须能够被调用方运行时稳定映射到 `service_name` 与 `namespace`，并通过 service discovery 完成实例解析。
- 服务标识符 URL 的推荐写法可以是：
  - `{logical_service_name}.{namespace}`
  - `{logical_service_name}.{namespace}.{zone}`
- 对于使用服务标识符的 URL，path、query、method 等 HTTP 语义必须保持不变；服务发现只负责解析目标实例，不得改变应用层接口语义。
- cross-system call 默认仍必须使用 stable entry 域名；只有在平台已明确约定服务标识符到跨 system 入口的映射关系时，才可以在 URL 中使用服务标识符表达跨 system 目标。
- 调用方不得仅凭 URL 字符串形式猜测目标是“普通域名”还是“服务标识符”；是否启用 service discovery 必须由显式配置或 option 决定。

#### 客户端实践原则
- client 应优先将目标 URL 固化为稳定域名或稳定服务标识符，而不是在业务代码中拼接实例地址、临时主机名或调试 IP。
- 当调用方采用服务标识符 URL 时，client 应通过显式 option 或等价配置表明是否启用 service discovery，而不得通过“看起来像服务名”进行隐式推断。
- 是否启用 service discovery 应作为 client 的可配置能力，而不是写死在业务调用逻辑中的分支判断。
- 当需要在调试、排障、灰度验证或临时诊断场景下指定实例时，client 应通过 option 覆盖实例选择结果，而不是修改业务代码中的目标 URL。
- 指定实例的调试 option 只能影响当前调用、当前 client 或显式作用域，不得默默污染全局默认行为。
- client 应将“服务发现启用开关”“实例覆盖”“zone 或 cluster 偏好”等能力设计为可扩展 option，以符合开闭原则。
- 即使 URL 中已写入服务标识符，client 运行时仍可能无法自动判断是否需要发现、走直连还是走普通 DNS；因此该行为必须由显式 option、配置或构造参数决定。
- client 在启用 service discovery 后，应保证默认调用路径仍面向健康实例集合；调试 option 只应用于受控场景，不得成为常规业务路径依赖。

#### client option 能力清单
- client option 的目标是把服务发现、实例选择、调试干预与缓存策略从业务 URL 和业务代码中解耦出来。
- 本规范不强制 option 的具体命名、函数签名或配置载体，但推荐 client 至少提供以下几类能力。

**发现开关类**
- `enable_service_discovery`
  - 用于显式表明当前调用或当前 client 是否启用 service discovery。
  - 当目标 URL 使用服务标识符时，应优先由该 option 决定是否进入发现逻辑。
- `service_namespace`
  - 用于补充或覆盖默认命名空间，避免调用方在 URL 中重复硬编码 namespace。
- `resolve_mode`
  - 用于声明发现模式，例如 `healthy_only` 或 `all`。
  - 业务默认值必须为 `healthy_only`。

**实例选择类**
- `preferred_zone`
  - 用于表达可用区、机房或等价拓扑偏好。
- `label_selector`
  - 用于声明硬过滤标签条件；未满足条件的实例不得返回。
- `preferred_label_selector`
  - 用于声明软偏好标签条件；未命中时可以回退到其他健康实例。
- `instance_picker`
  - 用于允许高级 client 注入自定义实例选择策略。
  - 自定义选择策略不得绕过健康筛选与基础治理约束。

**调试干预类**
- `instance_override`
  - 用于在调试、排障、灰度验证场景下直接指定单个实例或显式实例集合。
  - 该 option 只能用于受控场景，不得成为常规业务路径依赖。
- `disable_service_discovery_cache`
  - 用于临时关闭发现缓存，强制验证回源结果。
  - 该能力应默认关闭，并且应限制在显式调试作用域内使用。

**缓存与一致性类**
- `discovery_cache_ttl`
  - 用于覆盖 client 本地服务发现缓存时长。
  - 若服务端返回 `cache_ttl_ms`，client 不得把本地缓存时长放大到该上限之外。
- `force_refresh`
  - 用于在当前调用前强制刷新一次发现结果。
  - 即使启用强制刷新，也不得要求业务调用方自行分页拼装完整实例集合。
- `allow_stale_cache`
  - 用于在注册中心短暂不可用时，允许使用受控的陈旧缓存结果回退。
  - 启用后必须保留日志、指标或告警信号，明确当前结果来自缓存。

#### client option 设计约束
- option 必须优先作用于 client 运行时行为，而不是要求业务代码拼装特殊 URL、伪造 host 或修改 path 语义。
- option 的作用域必须清晰，至少应能区分“单次调用级”“client 实例级”和“全局默认级”。
- 用于调试的 option 必须默认关闭，并应尽量要求显式开启。
- option 之间存在冲突时，client 应定义明确优先级，并保持行为可预测、可文档化。
- option 的实现不得破坏“默认面向健康实例集合调用”的基本语义。

#### 响应字段

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| service_name | 是 | 本次查询命中的 logical service name。 |
| namespace | 是 | 本次查询实际生效的命名空间或隔离域。 |
| instances | 是 | 可用实例集合。若无可用实例，必须返回 `[]`，不得返回 `null`。 |
| resolve_time | 是 | 服务发现结果生成时间，推荐使用 RFC3339 或等价可比较时间格式。 |
| version | 否 | 结果版本、快照版本或等价修订号。用于缓存校验、增量更新或观测定位。 |
| cache_ttl_ms | 否 | 建议调用方本地缓存该结果的最长时间，单位毫秒。 |
| partial | 否 | 是否为降级、缓存回退或部分可用结果。默认应为 `false`；该字段不得用于表达“结果被截断”。 |
| warnings | 否 | 与本次结果相关的非致命告警信息，例如“结果来自缓存”或“治理规则已降级”。 |

#### 实例字段

| 字段 | 必须 | 说明 |
| --- | --- | --- |
| instance_id | 否 | 实例唯一标识。推荐返回，以便日志、指标与问题定位。 |
| host | 是 | 实例主机名、域名或 IP。 |
| port | 是 | 实例端口。 |
| scheme | 否 | 协议提示，例如 `http`、`https`、`grpc`。未提供时由调用方按服务默认配置解释。 |
| health_status | 是 | 健康状态。第一版应至少支持 `healthy`、`unhealthy`、`unknown`。默认查询只应返回 `healthy`。 |
| weight | 否 | 实例权重。用于加权路由或负载倾斜。 |
| zone | 否 | 实例所在可用区、机房或等价拓扑信息。 |
| labels | 否 | 实例标签集合。用于环境、灰度、拓扑与能力表达。 |

#### 响应语义
- `instances` 必须表示当前时刻面向当前调用方可用于发起调用的候选实例视图。
- `instances=[]` 表示查询成功，但当前无满足条件的可用实例；该结果与“服务不存在”必须严格区分。
- `partial=true` 表示结果来自缓存、降级路径或部分数据源；调用方可以继续使用该结果，但应记录日志或指标。
- `partial=true` 不得表示“实例结果被分页截断”或“尚有剩余实例需要继续拉取”。
- 当响应包含 `cache_ttl_ms` 时，调用方本地缓存不得超过该时长；未包含时，调用方应使用自身安全默认值。
- 当响应同时包含 `version` 与 `resolve_time` 时，调用方应优先将其用于缓存一致性校验与观测。

#### 大规模实例返回原则
- `instances` 表示面向当前调用方的候选实例集合，不要求等于底层 service registry 中的全量注册实例集合。
- 当服务实例规模较大时，实现可以基于拓扑优先级、治理规则、稳定采样、本地代理或等价机制返回受控候选子集。
- 受控候选子集必须满足当前查询条件、健康筛选规则与基本可用性要求，不得返回任意随机且不可解释的实例集合。
- 同一调用方在短时间窗口内获得的候选实例集合应尽量稳定，以减少连接抖动、负载震荡与缓存失效。
- 当实现返回受控候选子集时，调用方仍应将其视为完整可用视图，而不是继续拉取剩余实例。
- 面向业务调用方的发现协议不应承担“导出某服务全部注册实例”的职责；全量实例视图应由控制面、运维接口或专用诊断接口提供。
- 当调用方进程数较多或实例规模较大时，实现应优先采用本地缓存、watch、增量更新、节点代理、Sidecar 或等价机制降低 service registry 压力，而不应要求每次调用都回源全量查询。
- 如果结果来自缓存、本地代理或稳定采样，`partial` 可以用于表达该结果属于降级或非直连注册中心路径；但只要该结果仍可作为调用方候选集使用，就不得视为协议不完整。

#### 返回语义
- 查询成功且存在可用实例时，必须返回非空 `instances`。
- 查询成功但无可用实例时，必须返回空数组，并显式表达“无健康实例”或“无匹配实例”。
- 目标服务在当前命名空间下不存在时，必须返回“服务不存在”语义，而不得与“无健康实例”混淆。
- 查询失败时，必须返回可机器判断的失败类型，而不得要求调用方依赖错误文案做字符串匹配。
- 查询成功时，`instances` 必须已经是本次查询条件下的完整候选结果，而不是某一页结果。

#### 最小失败类型

| 失败类型 | 语义 | 调用方处理建议 |
| --- | --- | --- |
| service_not_found | 目标服务不存在 | 视为配置或部署错误，快速失败，不重试或仅有限重试。 |
| no_healthy_instance | 服务存在，但无满足条件的健康实例 | 可以按调用策略短暂重试，也可以触发熔断、降级或快速失败。 |
| discovery_timeout | 服务发现请求超时 | 受 `resilience` 规范约束；可以在剩余 quota 内有限重试。 |
| discovery_unavailable | 服务发现组件暂时不可用 | 可以使用本地缓存回退；若无缓存则按失败处理。 |
| invalid_request | 请求字段非法或缺失 | 视为调用方错误，必须立即失败。 |
| permission_denied | 调用方无权访问目标发现结果 | 视为安全或治理配置错误，必须立即失败。 |

#### 调用方处理要求
- 调用方必须区分“服务不存在”“无健康实例”“发现失败”三类结果，不得统一映射为同一种错误。
- 调用方可以对 `discovery_timeout` 与 `discovery_unavailable` 做有限重试，但重试必须受 `resilience` 规范约束。
- 调用方在使用缓存结果回退时，必须能够标记该结果来自缓存，并在日志或指标中保留可观测信息。
- 调用方不得因为发现协议返回了 `all` 或 `unhealthy` 实例，就绕过健康筛选直接发起业务调用，除非存在平台明确授权的诊断场景。

### 扩展治理能力

#### 范围
- 灰度、路由、限流、熔断属于服务间调用体系的一部分，可以在本规范范围内定义扩展能力。
- 当前版本只定义这些能力的接入边界与基础数据承载方式，不规定复杂策略模型、表达式语法或状态机细节。

#### 轻量约束
- 如果实现支持灰度或路由，相关规则必须优先绑定在 logical service name、实例元数据或 stable entry 上，而不是散落在业务代码中。
- 如果实现支持限流或熔断，策略的执行层可以位于调用方 SDK、网关、Sidecar 或平台代理层，本规范不强制限定。
- 治理能力的启用不得破坏服务发现的基础语义；在治理规则未命中时，调用方必须能够基于健康实例集合完成正常调用。

### 安全与可观测

#### 安全
- 通过外部域名、互联网域名或不受统一内网信任边界保护的 stable entry 发起的 cross-system call，必须使用 HTTPS 或等价加密传输机制。
- 通过团队内部域名、受控内网域名或明确处于统一信任边界内的 stable entry 发起的 cross-system call，可以不强制使用 HTTPS；但具体环境必须能够证明其网络边界、访问控制与风险接受策略满足安全要求。
- intra-system call 是否启用 TLS、mTLS 或等价机制，可以由具体环境决定，但不得妨碍统一的调用抽象与身份传递。
- 调用方在访问其他 system 时，必须能够绑定来源身份、租户、应用标识或等价认证信息。

#### 可观测
- 所有服务间调用都必须遵循 `tracing` 规范，透传 `ofa-pass-trace-id`、`ofa-direct-request-id` 与其他规定字段。
- 所有服务间调用都必须遵循 `resilience` 规范，统一处理 timeout quota、remaining timeout 与重试边界。
- 调用链路必须能够区分至少以下失败类型：服务不存在、无健康实例、连接失败、超时、上游治理拒绝、下游业务失败。
- 与服务发现相关的关键失败必须具备日志与指标，包括查询失败、缓存失效、实例全不健康与治理规则拒绝。

### 非目标
- 本规范不限制具体 service registry、网关、服务网格、SDK 或编程语言。
- 本规范不规定存量系统的迁移策略，也不强制要求既有系统在某个时间点完成收敛。
- 本规范不规定灰度算法、负载均衡算法、熔断状态机或限流令牌实现细节。

### 禁止事项
- 禁止跨 system 默认通过内部 logical service name 或实例地址直接访问目标服务。
- 禁止在 intra-system call 中写死实例 IP、节点地址或人工维护的静态实例清单。
- 禁止以无明确理由的方式默认引入 RPC 或其他非 HTTP 协议。
- 禁止让业务代码直接耦合具体 service registry 的专有实现。
- 禁止通过绕过 stable entry 的方式规避跨 system 的认证、审计、限流或治理边界。
- 禁止把服务发现与流量治理规则分散写入业务逻辑，导致调用语义不可审计、不可替换。

### 示例

#### 示例一：跨系统调用
- 订单 system 调用支付 system 时，必须访问 `pay.example.internal` 或等价 stable entry，而不得直接解析支付 system 内部的 logical service name。
- 支付 system 的域名入口后方可以连接网关、负载均衡或内部服务拓扑，但这些内部细节不得暴露给订单 system。

#### 示例二：系统内部调用
- 订单 system 内部的 `order-api` 调用 `inventory-service` 时，必须通过 `inventory-service` 的 logical service name 进行 service discovery。
- 具体由 DNS 解析到实例、由服务中心返回实例列表，或由 Sidecar 在本地完成实例选择，都属于允许实现。

#### 示例三：RPC 例外
- 某 system 内部存在高频流式日志订阅链路，需要双向流与长时间连接管理，可以采用 RPC。
- 采用 RPC 后，仍必须保证该链路具备接口定义、链路透传、超时约束、错误语义与可观测能力，而不得作为绕开规范的例外通道。
